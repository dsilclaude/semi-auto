# GPIB 와 VISA — 케이블을 바꾸면 코드의 어디가 바뀌나

이 문서는 `measauto` 가 장비와 어떻게 말하는지를 아래에서 위로 설명한다.
개념을 먼저 세우고, 실제로 이 PC 에서 겪은 오류들이 각각 어느 층에서
난 것인지 짚고, 마지막에 **무엇을 바꾸면 코드 어디를 고쳐야 하는지**를
표로 정리한다.

---

## 0. 결론부터

바꿀 게 생기면 고칠 파일은 거의 항상 **[`measauto/config.py`](../measauto/config.py) 하나**다.

| 무엇을 바꿨나 | 고칠 곳 | 예시 |
|---|---|---|
| GPIB 케이블만 새것으로 교체 | **없음** | — |
| 어댑터를 다른 USB 포트에 꽂음 | **없음** (보드 번호는 대개 유지) | — |
| 장비의 GPIB 주소를 바꿈 (17 → 20) | `b1500_address` | `GPIB0::20::INSTR` |
| 어댑터가 두 개가 되어 보드 번호가 밀림 | 두 주소 모두 | `GPIB1::17::INSTR` |
| 어댑터를 NI → Keysight 로 교체 | `visa_library` **와** 주소 | `ktvisa32.dll` + 새 보드 번호 |
| USB 어댑터 → LAN(LXI) 직결 | 주소만 | `TCPIP0::192.168.0.5::inst0::INSTR` |
| 장비를 다른 모델로 교체 | `drivers/` 의 해당 파일 | `b1500.py` |

배선(어느 프로브가 어느 SMU 인지)이 바뀌면 같은 파일의 `roles` 를 고친다.
그 위 층(`plan`, `metrics`, `agent`)은 **단자 이름만 알고 채널 번호를 모르므로**
건드릴 일이 없다.

## 1. 네 개의 층

```
   측정 코드          measauto/drivers/b1500.py        "스윕 해라"
        │
   ┌────▼────┐
   │  VISA   │        nivisa64.dll                    "GPIB0::17 에게 전해라"
   ├─────────┤
   │ NI-488.2│        ni4882.dll                      "보드 0, 주소 17"
   ├─────────┤
   │  어댑터  │        NI GPIB-USB-HS                  USB ↔ GPIB 통역
   ├─────────┤
   │  케이블  │        24핀 GPIB 케이블                전기 신호
   └─────────┘
        │
      장비            B1500A(주소 17) · S300(주소 28)
```

위층은 아래층의 사정을 모른다. 그래서 케이블을 바꿔도 측정 코드가 안 바뀌고,
반대로 **어느 층에서 문제가 났는지 모르면 엉뚱한 데를 고치게 된다.**

---

## 2. 물리층 — GPIB 와 주소

**GPIB**(General Purpose Interface Bus, IEEE-488)는 1970년대 HP 가 만든
계측기용 통신 규격이다. 요즘 기준으로 보면 이상한 물건인데, 실험실 장비가
20년씩 쓰이다 보니 아직도 현역이다.

핵심 성질 두 가지:

**하나의 케이블에 여러 장비가 매달린다.** 이더넷처럼 허브가 필요 없고,
장비 뒷면 커넥터에 다음 케이블을 겹쳐 꽂아 데이지체인으로 잇는다.
우리 셋업은 B1500A 와 S300 이 같은 버스에 있다.

**그래서 각 장비에 번호가 필요하다.** 이게 **GPIB 주소**로, 0~30 중 하나다.
장비 앞면 메뉴나 뒷면 딥스위치로 사람이 정한다.

```
B1500A  주소 17
S300    주소 28
```

이 숫자는 케이블이나 PC 가 정하는 게 아니라 **장비에 저장된 설정**이다.
케이블을 바꿔도 그대로고, 장비를 초기화하면 바뀔 수 있다.

**어댑터**(NI GPIB-USB-HS)는 PC 의 USB 와 GPIB 세계 사이의 통역기다.
PC 입장에서 어댑터는 그냥 USB 장치고, GPIB 버스 입장에서 어댑터는
'컨트롤러' 라는 특별한 참가자다.

---

## 3. 드라이버층 — NI-488.2 와 "보드 번호"

어댑터를 꽂으면 NI-488.2 드라이버(`ni4882.dll`)가 그것을 인식하고
**보드 번호**를 준다. 첫 번째 어댑터가 `GPIB0`, 두 번째가 `GPIB1` 이다.

> `GPIB0` 은 케이블 이름도, 장비 이름도 아니다. **어댑터에 붙은 이름**이다.

여기서 나는 대표적인 오류가 `EDVR` (`ibfind` 실패)이다. "그런 보드 모른다"는
뜻이고, 원인은 대개 어댑터가 드라이버에서 빠진 것이다. **장치관리자에
`Present` 로 보여도 그럴 수 있다** — Windows 의 PnP 상태와 NI 드라이버의
등록 상태는 별개이기 때문이다. 이걸 몰라서 "장치관리자에 멀쩡히 있는데
왜 안 되냐" 로 한참 헤맸다.

복구 방법은 하나뿐이었다: **USB 를 뽑았다 5초 뒤 다시 꽂기.**

---

## 4. VISA 층 — 표준 창구

**VISA**(Virtual Instrument Software Architecture)는 "장비와 말하는 법"의
표준 API 다. GPIB 든 USB 든 LAN 이든 시리얼이든 **같은 함수로 다루게**
해주는 게 존재 이유다. 그래서 우리 코드는 이렇게 생겼다:

```python
rm = pyvisa.ResourceManager(r"C:\Windows\System32\nivisa64.dll")
inst = rm.open_resource("GPIB0::17::INSTR")
inst.query("*IDN?")
```

장비가 LAN 으로 바뀌면 주소 문자열만 `TCPIP0::...` 로 바꾸면 되고
나머지 코드는 그대로다. 이게 VISA 가 주는 이득이다.

### 리소스 문자열 해부

```
GPIB0 :: 17 :: INSTR
  │       │      └── 리소스 종류. INSTR = 장비 하나.
  │       │          (INTFC = 버스 자체, SOCKET = 원시 TCP)
  │       └───────── GPIB 주소. 장비에 설정된 번호.
  └───────────────── 보드 번호. 어댑터에 드라이버가 준 이름.
```

### 함정: VISA 구현체가 여러 개다

VISA 는 **규격**이고, 그걸 구현한 DLL 은 회사마다 따로다. 이 PC 에는 둘 다 있다:

```
nivisa64.dll     National Instruments
ktvisa32.dll     Keysight
visa32.dll       ← 둘 중 하나로 넘겨주는 '라우터'
```

`pyvisa.ResourceManager()` 를 **인자 없이** 부르면 라우터(`visa32.dll`)를 탄다.
그리고 라우터가 어느 쪽으로 넘길지는 **설치 순서와 등록 상태에 따라 바뀐다.**
고정된 값이 아니다.

이게 왜 문제인지는 실제로 세 구현체에 같은 질문을 던져 보면 바로 보인다
(2026-08-21 실측):

```
기본 (visa32.dll)  ASRL1  GPIB0::17  GPIB0::11  GPIB0::28  GPIB1::11  GPIB2::17
NI 명시            ASRL1  GPIB0::17  GPIB0::28
Keysight 명시             GPIB0::11  GPIB0::28  GPIB1::11  GPIB2::17
```

읽는 법:

- **NI 만 실제 버스를 본다** — 주소 17, 28 두 대. 이게 사실이다.
- **Keysight 는 주소 11 을 보고한다.** 그런 장비는 우리 버스에 없다.
  Connection Expert 에 남아 있는 옛날 설정이 그대로 나오는 것이다.
- **같은 B1500A 가 NI 에서는 `GPIB0::17`, Keysight 에서는 `GPIB2::17`.**
- 기본(라우터)은 둘을 **합쳐서** 보여준다. 그래서 실재하지 않는 주소와
  실재하는 주소가 한 목록에 섞여 나온다.

여기서 얻을 교훈이 하나 있다:

> **보드 번호는 VISA 구현체마다 따로 매긴다.** `GPIB0::28::INSTR` 이라는
> 문자열 자체에는 "누구의 GPIB0 인가" 가 안 적혀 있다. 어느 DLL 에게 묻느냐에
> 따라 다른 장비를 가리킨다.

그래서 [`config.py`](../measauto/config.py) 는 DLL 을 **명시**한다.
라우터에 맡기지 않는다.

```python
visa_library: str = r"C:\Windows\System32\nivisa64.dll"
```

이 한 줄이 없으면 어느 날 갑자기 `VI_ERROR_RSRC_NFOUND` 가 나는데,
코드는 아무것도 안 바뀌었으니 원인을 찾기가 대단히 어렵다.
실제로 이 프로젝트에서 그랬다.

## 5. 세션 — 열었으면 닫아야 한다

`open_resource()` 가 하는 일은 **세션(session)을 여는 것**이다.
전화 통화에 비유하면 이렇다:

| 전화 | VISA |
|---|---|
| 전화번호 | 리소스 문자열 `GPIB0::17::INSTR` |
| 통화 연결 | `open_resource()` → 세션 핸들 |
| 통화 중 설정 (스피커폰 등) | `timeout`, `read_termination` … |
| 말하기 / 듣기 | `write()` / `read()` / `query()` |
| 끊기 | `close()` |

중요한 성질 두 가지다.

**첫째, 세션은 자원을 점유한다.** GPIB 장비는 보통 한 번에 한 세션만 받는다.
그래서 EasyEXPERT 가 B1500 을 잡고 있으면 우리 코드가 못 연다. 반대도 같다.

**둘째, 안 닫으면 남는다.** 파이썬 프로세스가 정상 종료하면 세션이 정리되지만,
**강제 종료하면 정리 단계가 실행되지 않는다.** 그러면 드라이버 쪽에는
"열려 있는 세션" 기록이 남고, 어댑터가 그 상태로 굳는다.

이 프로젝트에서 강제 종료한 뒤 매번 `GPIB0` 이 통째로 사라진 이유가 이것이다.

```
강제 종료 → 세션이 안 닫힘 → 드라이버 상태 꼬임 → GPIB0 이 목록에서 사라짐
          → USB 재연결로만 복구
```

그래서 `measauto` 는 측정마다 **시간 상한**을 건다. 상한에 걸리면 스스로
끝나면서 `close()` 를 부르기 때문에, 사람이 죽일 일이 안 생기게 하려는 것이다.

`timeout` 은 **세션의 속성**이라는 점도 알아둘 만하다. 장비 설정이 아니라
"이 통화에서 얼마나 기다릴 것인가" 다. B1500 은 스윕이 길어서 300초,
S300 은 이동이 끝날 때까지 30초로 잡아 뒀다.

## 6. 오류 사전 — 실제로 본 것들

| 오류 | 어느 층 | 뜻 | 대응 |
|---|---|---|---|
| `VI_ERROR_RSRC_NFOUND` | VISA | 그 주소에 아무것도 없다 | 어댑터 빠짐, 또는 **틀린 VISA 구현체**를 봤다 |
| `EDVR` / `ibfind` 실패 | 드라이버 | 그런 보드 모른다 | USB 재연결 |
| `VI_ERROR_TMO` | 세션 | 열리긴 했는데 답이 없다 | 장비 전원·주소 확인, `clear()` |
| `VI_ERROR_BERR` | 물리/드라이버 | 버스 오류 | 케이블·종단, 다른 컨트롤러와 충돌 |
| `VI_ERROR_ABORT` | 세션 | 진행 중 동작이 중단됐다 | 버스가 꼬였다 — 재연결 |
| `ENOL` | 드라이버 | 듣는 장비가 없다 | 주소 틀림, 장비 꺼짐 |

**진단 순서는 항상 아래층부터다.**

```
1. GPIB0 이 목록에 보이나?          안 보이면 → 어댑터/드라이버 문제. USB 재연결.
2. 주소가 목록에 보이나?             안 보이면 → 장비 전원·케이블·주소.
3. *IDN? 에 답하나?                 답 없으면 → 세션 문제. clear() 후 재시도.
4. 그래도 안 되면                   다른 프로그램이 잡고 있나 확인.
```

이 순서를 [`executor._check_bus()`](../measauto/executor.py) 가 자동으로
1·2단계까지 해 준다. 장비를 열기 **전에** 확인하므로, 실패해도 팁은
접촉된 자리에 그대로 있고 안전하다.

한 가지 함정: **장비가 죽은 것처럼 보이는데 사실은 버퍼가 막힌 것**일 때가
있다. B1500 을 켠 직후 `BERR → IO → TMO` 가 연달아 났는데, 원인은 아무도
안 읽어간 출력이 버퍼에 남아 있던 것이었다(STB=0x30). `clear()` 한 번으로
풀렸다. 정상 연결 경로는 이미 `clear()` 를 부르므로 저절로 해결된다.

## 7. 무엇을 바꾸면 어디를 고치나 (상세)

### 케이블만 교체

**고칠 것 없다.** 케이블은 어떤 소프트웨어 층에도 이름이 없다.
새 케이블을 꽂고 장비 전원을 확인하면 끝이다.

### 장비의 GPIB 주소 변경

장비 앞면에서 주소를 17 → 20 으로 바꿨다면:

```python
# measauto/config.py
b1500_address: str = "GPIB0::20::INSTR"     # 17 → 20
```

### 어댑터를 다른 USB 포트로

보통 보드 번호(`GPIB0`)가 유지되므로 **고칠 것 없다.**
확인은 아래 명령 한 줄이면 된다.

### 어댑터를 하나 더 꽂았거나 교체해서 보드 번호가 바뀜

새 어댑터가 `GPIB1` 을 받았다면 **주소 문자열 두 개를 다** 고친다:

```python
s300_address:  str = "GPIB1::28::INSTR"
b1500_address: str = "GPIB1::17::INSTR"
```

### 어댑터를 NI → Keysight 로 교체

**두 군데를 고쳐야 한다.** 이게 제일 헷갈리는 경우다.

```python
visa_library:  str = r"C:\Windows\System32\ktvisa32.dll"   # ① DLL 교체
b1500_address: str = "GPIB0::17::INSTR"                    # ② 보드 번호 재확인
```

4장에서 봤듯 Keysight 의 `GPIB0` 과 NI 의 `GPIB0` 은 **다른 것**이다.
DLL 만 바꾸고 주소를 그대로 두면 엉뚱한 곳을 가리킬 수 있다.
반드시 새 DLL 로 목록을 다시 뽑아 확인한다.

### LAN(LXI) 장비로 교체

```python
b1500_address: str = "TCPIP0::192.168.0.5::inst0::INSTR"
```

주소 형식만 다를 뿐 나머지 코드는 그대로다. **이게 VISA 를 쓰는 이유다.**

### 프로브 배선 변경

GPIB 와는 무관하지만 같은 파일에 있다.

```python
roles = {"BG": 1, "D": 2, "S": 3}    # 단자 이름 → SMU 채널
```

`roles` 에 없는 단자를 `plan` 이 건드리면 `executor` 가 막는다.
(참고: `smuN` 은 슬롯 번호가 아니다. 실측으로 `smu1→슬롯2` 임을 확인했고
그 근거가 `config.py` 주석에 남아 있다.)

## 8. 확인 명령

무엇을 바꿨든, 바꾼 뒤에는 이걸 돌려 본다.

```powershell
cd e:\semi-auto
.\.venv\Scripts\python.exe -c "import pyvisa; print(pyvisa.ResourceManager(r'C:\Windows\System32\nivisa64.dll').list_resources())"
```

기대하는 출력:

```
('ASRL1::INSTR', 'GPIB0::17::INSTR', 'GPIB0::28::INSTR')
```

- `GPIB0` 이 통째로 없으면 → **USB 재연결**
- 주소 하나만 없으면 → 그 장비의 전원·케이블·주소
- 목록에 있는데 측정이 안 되면 → 세션 문제 (5·6장)

`ASRL1::INSTR` 은 COM 포트(시리얼)다. GPIB 와 무관하고 우리는 안 쓴다.

## 부록 — 이 프로젝트에서 실제로 겪은 것

시간순으로 정리한 사건과 원인이다. 같은 일이 또 생기면 여기부터 본다.

| 증상 | 진짜 원인 | 교훈 |
|---|---|---|
| 버스 전체가 `VI_ERROR_ABORT` | `GPIB0::INTFC` 를 열고 `clear()` 를 걸었다 | 버스 자체(`INTFC`)는 함부로 건드리지 않는다 |
| Keysight VISA 가 NI 보드를 잡고 있다고 판단 | **틀린 가설이었다.** Keysight 의 GPIB0 은 없는 82357B 를 가리키는 옛 설정이었다 | 가설은 검증하고 나서 믿는다 |
| `ibfind` 가 없다는 오류 | 64비트 `ni4882.dll` 은 `ibfindA` 로 내보낸다 | 32/64비트에서 export 이름이 다르다 |
| 껐다 켜도 계속 안 됨 (5회 이상) | 강제 종료 → 세션 미정리 → 드라이버 고착 | **강제 종료하지 않는다.** 대신 시간 상한을 건다 |
| B1500 이 켠 직후 응답 없음 | 출력 버퍼에 안 읽어간 데이터 (STB=0x30) | `clear()` 한 번으로 풀린다 |
| off 전류가 항상 5e-12 A | 소자가 아니라 `1 nA` 측정 레인지의 바닥 | 측정계 한계와 소자 특성을 구분한다 |

가장 자주 필요했던 조치는 결국 **USB 재연결** 하나였다. 어댑터가 드라이버에서
빠지는 것이 이 셋업의 고질적 약점이고, 장치관리자를 아무리 봐도 알 수 없다.
`list_resources()` 에 `GPIB0` 이 보이는지가 유일하게 믿을 만한 신호다.
